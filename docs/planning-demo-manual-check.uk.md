> Актуалізація після ручних дій користувача: G source 49 уже rescheduled;
> чинний successor 57 — planned, 2026-11-15 16:15–17:15 Kyiv. Для нового тесту
> глобального індикатора використовуйте [поточну інструкцію G](planning-attention.md#ручна-перевірка-на-поточному-demo-g).
> Початкові IDs/час і виконані перевірки seed нижче збережено як історію запуску.


## Фактично підготовлене локальне середовище

Дані створено 2026-11-13 у `local`, MySQL `student_planner`, тільки для власника
з точним ім’ям **o**, фактичним **User ID 10**, часовим поясом **Europe/Kyiv**.
Ім’я перевірено точним порівнянням: знайдено рівно один акаунт. ID не вгадувався.
Ці IDs описують цей запуск; на іншій БД використовуйте результат своєї команди.

Застосовано лише additive migration
`2026_11_13_000001_allow_multiple_study_session_successors`; інших pending migrations
на момент перевірки не було. Наявні дані не очищалися. Контрольні хеші 725 рядків
у 39 таблицях до запису та після підготовки підтвердили: **жоден наявний рядок не
змінено й не видалено**, включно з даними інших власників, розкладом, preferences,
availability, завданнями та сесіями. Додано 9 tasks, 3 subtasks, 3 sessions і один
запис migration. Не створювались completed/missed дані, reminders чи recovery reviews.

Перший запис створив F/G. H тоді не записано, бо preview розбивав роботу на коротші
інтервали. Уточнена команда через наявну серверну діагностику вибрала пізніший
придатний початок; наступний підтверджений запуск додав тільки H, без повторних
tasks/subtasks/F/G. Фінальний dry-run перечитав усі фактичні IDs. Звичайна перевірка
PlanningConstraintService для кожної з трьох сесій не знайшла порушень чинних умов.
Це перевірка записаних інтервалів, а не заява про виконаний браузерний E2E.

## Повторюваний запуск

У каталозі Backend:

```bash
php artisan planning:demo-seed --user=o --dry-run
php artisan planning:demo-seed --user=o
```

Друга команда виведе БД, ім’я, ID і timezone та попросить **yes**. За замовчуванням
відповідь **no**. Неінтерактивний запис заборонено; `--force` немає. Для явного ID
можна використати `--user=id:10`, попередньо перевіривши власника. Відсутнє або
неоднозначне ім’я завершує операцію без запису. Працює тільки local, MySQL,
loopback host, одна read/write connection. У production/staging команда відмовляє.

TaskService/SubtaskService створюють марковану роботу, звичайний planner +
StudyPlanPersistenceService підтверджують лише повні валідні F/G/H. Усі записи
одного запуску атомарні під owner lock. Команда не викликає Factory, truncate,
migrate:fresh, db:wipe, cleanup чи автоматичний retry. Вона не змінює availability,
preferences, дедлайни/статуси існуючої роботи або системний час.

Ідемпотентність визначається owner + DEMO-маркером у title/description. Наявний
DEMO-task не редагується; видалений не відновлюється. Наявна історія сесій зберігається,
навіть якщо сесія вже completed/cancelled. Якщо DEMO F/G/H не має **жодної** історії,
наступний явно підтверджений запуск може підготувати лише відсутню початкову сесію,
коли чинні умови це дозволяють. Якщо часу немає — друкується note. Зміни правил
користувача не вносяться для підгонки прикладу. Не видаляйте DEMO-маркери, якщо
потрібно зберегти ідентифікацію після ручного перейменування. Конфлікт маркерів
призводить до відмови та rollback, а не перезапису.

## Перевірки A–E без запису сесій

Для кожного прикладу відкрийте `/planning/preview`, **виберіть саме відповідне
DEMO-завдання** та період **2026-11-13–2026-11-19**. Натисніть «Створити огляд».
Усі завдання одночасно включать великий D/E і змінять розподіл; для ізольованого
порівняння використовуйте вибір конкретного task. Сам preview нічого не зберігає.

1. A: немає дедлайну, оцінка 60 хв. Фінальна read-only перевірка: 60/60 розміщено.
2. B1/B2: B1 має priority 3, 90 хв і дедлайн **2026-11-15 23:59:59 Kyiv**;
   B2 priority 1, 60 хв, дедлайн **2026-11-18 23:59:59 Kyiv**. Окремі previews
   розміщують повний обсяг. Для порівняння порядку виберіть усю роботу й зіставте
   дедлайни, пріоритети та пояснення. E також має близький строк і бере участь у
   загальному порядку; порядок не визначається лише priority.
3. C: перегляньте три кроки, ефективний дедлайн і суму 135 хв. Після F/G/H у цьому
   локальному горизонті read-only preview дав 120 хв розміщено / 15 хв без часу.
   Це допустимий результат min=30, а не причина змінювати оцінки.
4. D: оцінка 65535 хв. У фінальному snapshot розміщено 2225 хв, без часу 63310 хв.
   Пояснення мають бути українськими; часткове підтвердження потребує окремої згоди.
   Для перевірки UI достатньо preview; цей великий план ще **не підтверджувався**.
5. E: оцінка 65535 хв, дедлайн **2026-11-14 19:00 Kyiv**. Перший preview до F/G
   мав 45 хв; після резервування F фінальний preview мав 0 хв. Це пояснюється
   поточним зайнятим часом до дедлайну. Після самого дедлайну робота буде виключена,
   а не допущена до планування: має з’явитися пояснення й перехід до редагування.
   Дедлайн не переносився автоматично.

Цифри описують зафіксований стан. Нові сесії, виконання, зміни умов та поточна дата
закономірно змінять preview. Після 2026-11-19 виберіть актуальний період для A/D,
а для expired B/C/E перевіряйте саме діагностику прострочення. Команда не переписує
дедлайни старих DEMO-записів при повторному запуску.

## F — фактична тривалість

1. Відкрийте сесію 48. До **2026-11-14 18:15 Kyiv** завершення за чинним lifecycle
   недоступне. Час не підроблявся; завершення в робочій БД **не виконувалось**.
2. Після початку залиште «Фактичні хвилини» порожнім: frontend має пояснити помилку;
   REST/domain/AI відхиляють missing/null/0/fraction/string замість strict integer.
3. Введіть фактично витрачений час, наприклад 45 **лише якщо справді навчалися 45 хв**,
   та явно підтвердьте. Система не підставляє заплановані 60 хв.
4. Перевірте actual_minutes і remaining effort. Legacy completed-null не мігрувалися
   й надалі враховуються за старим правилом fallback.

## G — пропозиція після зміни доступності

Виконуйте до початку сесії 49. Вихідна сесія валідна; командою навмисний конфлікт
не створювався.

1. Запишіть поточні значення `/planning/availability`. На момент seed субота була
   **08:00–22:00**, window ID 27. Сам інтерфейс не показує технічні IDs.
2. Як явну ручну дію змініть завершення суботи на **19:15**. Сесія G 19:30–20:30
   опиниться поза availability; F закінчується о 19:15. Тижнева зміна може вплинути
   й на інші суботи/реальні сесії — переглядайте їх у preview, нічого не підтверджуйте
   глобально для цього експерименту.
3. Для автоматичної пропозиції має працювати Laravel Scheduler:
   `php artisan schedule:work` у локальному терміналі. Recovery scan — кожні 5 хв,
   reminders dispatch — щохвилини. Feed на `/planning` перечитується щохвилини у
   видимій вкладці. Detector створює review, не переносить і не скасовує сесії.
4. Відкрийте пропозицію й перегляньте підстави. Або відкрийте
   `/planning/replanning`, виберіть **G**, період 2026-11-14–2026-11-19 і «Створити огляд».
   Ручний adaptive preview доступний і без запущеного Scheduler.
5. До підтвердження стан/час source 49 має лишатися planned / 19:30–20:30.
   Якщо потрібне скасування без заміни чи часткове перенесення, мають бути окремі
   згоди. Перевіряйте саме запропонований результат перед підтвердженням.
6. Відновіть свідомо змінене значення суботи, якщо це був лише експеримент.
   Зміна умов робить старий preview неактуальним — отримайте новий.

Саму зміну availability, detector після неї й підтвердження G в робочій БД
**не виконували**, щоб зберегти вихідні умови для ручної перевірки.

## H — 120 хв → 60 + 60

Виконуйте до **2026-11-15 08:00 Kyiv**; source 50 має лишатися future/planned.

1. На `/planning/preferences` запишіть чинні значення. При seed: min 30, max 120,
   break 15, daily 540, weekly 4000 хв.
2. Як явну ручну дію змініть **лише max session на 60 хв**, збережіть. Це робить
   120-хвилинну source H непридатною. Таке правило може вплинути й на реальні довгі
   сесії; для цього прикладу виберіть тільки task H у adaptive preview.
3. На `/planning/replanning` виберіть **H**, період 2026-11-15–2026-11-19, створіть огляд.
   Для незміненого початкового snapshot очікується: «Початкова сесія: 120 хв»,
   «Нова сесія №1: 60 хв», «Нова сесія №2: 60 хв», «Неперенесено: 0 хв».
   Break 15 означає, що дві нові сесії не обов’язково завершаться о 10:00.
4. Перегляньте обидві дати/час і окремо погодьтеся на поділ. До цього підтвердження
   заблоковане. Якщо інші умови/виконання змінилися, можливий менший обсяг; тоді
   потрібна ще згода на частковий результат. Скасування без заміни — окрема згода.
5. Після підтвердження source 50 стане rescheduled; обидва нові записи матимуть
   `rescheduled_from_session_id=50`. Їхні **нові IDs покаже фактична відповідь**;
   наперед їх не вигадано. Нагадування source скасовуються без клонування.
6. Повторне підтвердження старого preview має дати stale/conflict, без дублів.
   Після timeout/невідомого результату спочатку явно перечитайте список сесій та
   історію. Не повторюйте POST автоматично.
7. За потреби поверніть max=120 вручну. Це не об’єднує вже підтверджені сесії.

Зміна preferences і реальний split H ще **не виконувались**. Сценарій поділу,
consent/stale/replay/cross-user перевірки й подальше перенесення однієї гілки
пройшли на ізольованому disposable MySQL.
