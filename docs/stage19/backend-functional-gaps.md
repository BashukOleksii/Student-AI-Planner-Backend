# Stage 19A-BE — Backend functional gaps and evidence limits

Baseline: `1912ff45be03d5eed3dfeabe5fa6a1a2f13958a4` on `main`, 2026-11-08. Original groups are pinned to Frontend `a3bfbde90f9d1a5d1e30a80155153f824f03b068`; see the [48-group audit](backend-requirements-audit.md). This register recommends future work only. No fix, new contract, test or migration is implemented here.

P0 means a security/data-integrity blocker; P1 mandatory missing behavior; P2 incomplete integration, quality or verification; P3 optional enhancement. **No P0 defect or unambiguously mandatory P1 omission was confirmed in the inspected Backend paths.** This bounded audit cannot prove the absence of every defect. Literal reminder deletion, Task-pair conflict wording and background autonomy require explicit interpretation before assigning a mandatory system failure. Frontend completeness has not been assessed.

## Confirmed missing behavior and limited integration

### G19-01 — Task-to-Task conflict identities are not returned

- **Requirement / priority:** R28, **P2**, incomplete explanation contract; mandatory meaning requires clarification.
- **Implemented:** Stage 17 provides deterministic priority rank, per-work allocation reasons, recommendation codes and measured persisted workload alerts. This resolves much of the historical gap.
- **Missing:** a response identifying particular conflicting Task pairs and explaining their relationship. `work_advice` includes individual work IDs/reasons; `persisted_workload_violations` identifies daily/weekly periods and totals. Neither is a Task-pair explanation. Tasks themselves have no scheduled interval; StudySessions do.
- **Evidence / components:** [WorkloadAdviceService](../../app/Services/Planning/WorkloadAdviceService.php)::analyze/recommendations/persistedViolations; [WorkloadAdviceResource](../../app/Http/Resources/WorkloadAdviceResource.php); [PlanningConstraintService](../../app/Services/Planning/PlanningConstraintService.php)::evaluate; [Stage 17 contract](../stage17/workload-advice-api-contract.md). No pair field exists in their emitted shape.
- **Recommended small change:** first decide whether “conflicts between Tasks” means the existing capacity/constraint evidence or identifiable competing reservations. If pair evidence is required, add a read-only explanation from the same owner-scoped planning context and interval rules. Do not create an optimizer, change priority scoring or claim mathematical infeasibility.
- **Dependencies / security:** agreed interval/status/Task attribution and bounded evidence shape; use owned Tasks/Subtasks/sessions, fail closed on incompatible references, preserve constant/batched source loading and read-only behavior.
- **Acceptance:** either explicitly accept the existing warning semantics in requirements documentation, or expose bounded, deterministic reservation conflict evidence that names only owned affected work and states its provenance. A greedy shortfall must remain distinct from proof of impossibility.
- **Required PHPUnit:** overlapping and adjacent sessions, multiple sessions for one Task, foreign-user isolation, incompatible history, capacity shortfall without a conflicting pair, duplicate/tie ordering, bounded output and unchanged all-table snapshots. Preserve [WorkloadAdviceApiTest](../../tests/Feature/WorkloadAdviceApiTest.php).
- **Frontend dependency:** inspect current warning labels and priority rendering before claiming this is a system-wide missing interaction. The existing endpoint already supports useful advice.

### G19-02 — Literal Reminder deletion is absent

- **Requirement / priority:** R32, **P3 pending a semantics decision**. The absence is confirmed; mandatory hard deletion is not agreed.
- **Missing:** there is no `DELETE /api/reminders/{reminder}`, deletion Service operation or AI deletion Tool. Scheduled cancellation retains the Reminder row; sent/cancelled history and inbox notifications survive.
- **Evidence / components:** [routes/api.php](../../routes/api.php), [ReminderController](../../app/Http/Controllers/Api/ReminderController.php)::cancel, [ReminderService](../../app/Services/Reminders/ReminderService.php)::cancel, [ReminderMutationService](../../app/Services/Reminders/ReminderMutationService.php)::cancel, [SubtaskReminderActionRegistry](../../app/Services/AI/Actions/SubtaskReminderActionRegistry.php). [ReminderApiTest](../../tests/Feature/ReminderApiTest.php) verifies the existing lifecycle.
- **Recommended small change:** resolve whether cancelling an active Reminder satisfies the original “delete” story. If yes, document that accepted meaning and align UI wording. If literal removal is adopted, specify eligible statuses and inbox/receipt retention before adding a narrow Service operation; do not reinterpret existing cancellation or erase historical receipts.
- **Dependencies / security:** retention decision, notification FK/history behavior, owner-first serialization and delivery/cancellation races; one authenticated owned target only. Existing AI cancel proposals must keep their contract.
- **Acceptance:** an explicit recorded interpretation, accurate UI labels and safe handling of already sent reminders. Any future removal must leave durable AI receipts and historical notifications interpretable.
- **Required PHPUnit if removal is approved:** owned/foreign/missing IDs, sent/cancelled eligibility, concurrent delivery/removal, unchanged work/session records, notification-history integrity, rollback and existing cancellation regression. No deletion implementation test can pass for the current absent operation.
- **Frontend dependency:** determine whether the current UI promises cancellation or permanent removal. Do not infer a Backend delete contract from a button label.

### G19-03 — Unattended relocation has no trigger or execution policy

- **Requirement / priority:** R48; broader interpretation of R10/R24, **P3**, optional scope decision.
- **Missing:** a scheduled/event-driven process that detects unfinished work and relocates it without a user-launched review. Interactive remaining-work planning and adaptive replanning are implemented.
- **Evidence / components:** [routes/console.php](../../routes/console.php) schedules only `reminders:dispatch-due`; [TaskService](../../app/Services/Tasks/TaskService.php)::miss changes status without planning; [StudyRecoveryPreviewService](../../app/Services/Planning/StudyRecoveryPreviewService.php)::preview is read-only; [StudyReplanningPersistenceService](../../app/Services/Planning/StudyReplanningPersistenceService.php)::confirm requires protected review and consent. The only application Job is [SendPasswordResetLink](../../app/Jobs/SendPasswordResetLink.php).
- **Recommended small change:** decide the desired trigger and persisted user consent before implementation. A future background adapter should compose existing deterministic selection/planning/persistence under current ownership/concurrency rules. It must not add a second rescheduling engine or let an LLM execute automatically.
- **Dependencies / security:** explicit product approval for autonomous changes, consent/revocation, clock/late-work policy, idempotent trigger identity, stale review behavior, bounded scope and receipt/history retention. Current conversational confirmation requirements cannot be weakened implicitly.
- **Acceptance if approved:** predictable opt-in execution, at-most-once business effects per trigger, current-state constraints/deadlines, preserved missed/completed history, safe no-capacity handling and visible durable outcomes. Otherwise retain the current interactive contract and describe it accurately.
- **Required PHPUnit:** trigger eligibility, revoked/missing consent, duplicate/concurrent triggers, owner races, changed timezone/deadline/availability, no capacity, partial-result policy, unexpected failure rollback and unchanged unrelated domains.
- **Frontend dependency:** check recovery UI and explanations. A recovery button or AI proposal is not evidence of autonomous operation.

### G19-04 — Optional team/calendar/AI-import/deployment ideas remain incomplete

- **Requirement / priority:** R47, **P3**, explicitly development directions rather than mandatory S1/S2 behavior.
- **Missing:** team/common availability and shared authorization model; calendar export/integration; an AI Excel-import Tool; automated container/staging deployment/promotion/rollback in the checked-in Backend workflow. Manual XLSX import and offline CI are implemented.
- **Evidence / components:** [routes/api.php](../../routes/api.php); [ToolRegistry](../../app/Services/AI/Tools/ToolRegistry.php) and action registries; [ScheduleImportController](../../app/Http/Controllers/Api/ScheduleImportController.php); sole [Backend verification workflow](../../.github/workflows/backend-verification.yml). No corresponding route/Tool/workflow step was found.
- **Recommended small change:** choose one separately approved integration, not a bundle of speculative features. Reuse current schedule/import Services. Calendar export could be a read-only bounded adapter; AI import would need upload/review provenance and the existing commit semantics. Team features require an explicit access model first. Deployment requires an isolated operational design.
- **Dependencies / security:** agreed external provider/format and secrets policy, participant consent/access revocation, import ownership and review provenance, deployment credentials and environment separation. No external integration may widen personal-data access implicitly.
- **Acceptance if approved:** one documented contract with owned/bounded data, no unconfirmed writes, safe failures and separately demonstrated deployment or integration outcomes.
- **Required PHPUnit:** relevant export range/timezone/isolation cases, import preview/stale/commit regression, team membership/revocation checks if selected; deployment smoke/recovery checks are operational evidence in addition to PHPUnit.
- **Frontend dependency:** Frontend build/E2E/hosting and calendar UI are outside this Backend finding. No system-wide failure is assigned for unapproved development ideas.

### G19-05 — AI academic catalog discovery is absent

- **Requirement / priority:** R21 and usability of R07/R20, **P2**, integration limitation; the confirmed Lesson action capability remains implemented.
- **Missing:** allowlisted reads that resolve Subject, Teacher or AcademicPeriod names into owned identifiers. Lesson creation/replacement requires an exact Subject ID; unknown catalog IDs require clarification or explicit user input. Existing schedule/Task reads can ground only identifiers already present in their results.
- **Evidence / components:** [AgentOrchestrator](../../app/Services/AI/AgentOrchestrator.php)::instructions explicitly states no catalog discovery Tool is available; [LessonActionRegistry](../../app/Services/AI/Actions/LessonActionRegistry.php)::definitions; [LessonInputRules](../../app/Services/Schedule/LessonInputRules.php); REST catalog controllers already exist.
- **Recommended small change:** if natural-name creation is expected, add a bounded, owner-scoped catalog lookup adapter around the existing academic Services. Keep ambiguity handling and exact-ID proposal validation. Do not allow inferred associations or arbitrary dispatch.
- **Dependencies / security:** decide catalog search/matching and pagination semantics; preserve same-owner institution/reference validation and foreign-ID masking. No mutation framework or schema change should be necessary for a read adapter.
- **Acceptance:** discover only owned candidates, require clarification for ambiguity, and feed an exact ID into the unchanged confirmed Lesson flow. Existing 31 definitions/contracts remain compatible.
- **Required PHPUnit:** empty/ambiguous search, bounds/unknown arguments, cross-user catalog isolation, discovery-to-proposal fake-provider sequence, exact-ID validation and existing Lesson confirmation regression.
- **Frontend dependency:** inspect academic selectors and exact-ID affordances before deciding the severity of this usability limitation.

### G19-06 — Login and registration have no application rate limiter

- **Requirement / priority:** R41/R42/R45 account protection, **P2 security hardening; address before optional functionality**. Core login/ownership behavior is implemented; rate limiting is not separately specified as an original story. This is a confirmed application guard omission, not a demonstrated account takeover or a statement about an uninspected gateway.
- **Missing:** login/registration routes have no throttle middleware, global API throttling or per-credential attempt limiter in their Controller/Requests. Password recovery/reset/change and AI messages do have explicitly attached named rate limiters.
- **Evidence / components:** [routes/api.php](../../routes/api.php) public auth group; [AuthController](../../app/Http/Controllers/Api/AuthController.php)::register/login; [LoginRequest](../../app/Http/Requests/Auth/LoginRequest.php), [RegisterRequest](../../app/Http/Requests/Auth/RegisterRequest.php); [bootstrap/app.php](../../bootstrap/app.php) middleware configuration; [AppServiceProvider](../../app/Providers/AppServiceProvider.php)::boot defines only password and AI limiters. Repository-wide rate-limit search confirmed no login/registration limiter. No attack or live authentication loop was run.
- **Recommended small change:** use Laravel's existing rate-limiting middleware with deliberate shared-cache keys/budgets for login attempts and registration, preserving uniform invalid-credential errors and CSRF/session rules. Keep Controllers thin; do not introduce another auth framework or infer that CORS is an attempt limiter.
- **Dependencies / security:** agreed attempt/registration budgets, trusted proxy/IP configuration and a shared cache for multiple workers. Avoid account-existence disclosure or permanent user lockout. Gateway policy may complement the application guard but was not inspected here.
- **Acceptance:** repeated attempts reach a safe 429 with retry metadata before unbounded credential hashing/account creation; normal authentication, session rotation, ownership isolation and recovery throttling remain correct. If a verified gateway-only policy is intentionally chosen, document and test that dependency explicitly.
- **Required PHPUnit:** repeated invalid login attempts, unknown versus existing-account response parity, IP/identity key separation, reset after the limit window, successful login behavior, registration bounds, shared-worker cache behavior, CSRF and current auth regression. [AuthProfileTest](../../tests/Feature/AuthProfileTest.php) currently verifies credentials/session/CSRF, not login throttling.
- **Frontend dependency:** render retry feedback without retry loops; do not claim deployment exposure or protection without actual gateway/runtime evidence.
