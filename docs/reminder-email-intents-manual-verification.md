# Ручне приймання поштових намірів — 2026-11-14

## Зміна

Міграція: `database/migrations/2026_11_14_000003_create_reminder_email_intents.php`.
Команда: `php artisan reminders:dispatch-email-intents --limit=100`.
Scheduler викликає її щохвилини; допустимий пакет — 1–1000.
Worker залишається чинним:

```sh
php artisan queue:work reminder-email --queue=reminder-email --sleep=3 --tries=3 --timeout=60
```

Inbox, `sent` та намір комітяться разом. В окремій транзакції job та `queued_at`
комітяться разом. `queued_at` не означає «лист надіслано». Гарантії одноразової
SMTP-доставки немає: невизначена відповідь SMTP або падіння worker після send
можуть дати дублікат при повторі чинного job. Політика SMTP-повторів не змінена.

Історичні міграції, `SendReminderEmail`, автоматичні нагадування перед сесіями,
ручне відновлення, Frontend, SMTP-конфігурація та AWS не змінювалися. Намірів для
історичних сповіщень немає; старі jobs не потребують нового запису для виконання.

## Середовище і спосіб перевірки

Перед змінами `git status --short` був порожній, гілка `main`. Прочитано інструкції,
сервіси доставки/пошти, job, queue config, Scheduler, міграції й пов'язані моделі,
документацію та виклики `processWithinTransaction`: public `process()`, demo writer,
попередній ручний звіт і перевірку guard у наявному тесті. Автоматизованих тестів
не додавали, не редагували й не запускали.

Використано ізольовану локальну MySQL із новим datadir у тимчасовому каталозі,
`--skip-networking`, окремим socket і БД `planner_email_intents`. `SELECT @@datadir`
підтвердив ізоляцію перед міграціями. Усі міграції, включно з новою, застосувалися.
Окремі процесні DB env, APP_KEY і APP_CONFIG_CACHE не змінювали `.env` та робочу БД.
Чинний Mailpit на `127.0.0.1:1025` / `:8025` не перезапускався; листи не видалялися.
Рахували лише синтетичні адреси поточного приймання; фінальний підрахунок
фільтрував точну адресу в Mailpit `To`, бо пошук `to:` збігається й за підрядком.

Ручні PHP CLI-сценарії поза репозиторієм завантажували звичайний Laravel kernel,
викликали справжні Services, Artisan та SMTP worker. Немає PHPUnit/Pest, fakes,
тестових класів або змін `tests/`. Це перевірка сервісів/БД/worker, не HTTP чи UI.

Фактично перевірена queue config: `driver=database`, `connection=null`,
`table=jobs`, `queue=reminder-email`, `after_commit=false`, `retry_after=90`.
Об'єкт connection черги тотожний доменному `DB::connection()`, driver — MySQL.
`jobs`, `notifications`, `reminders`, `reminder_email_intents` фактично InnoDB.

## Отримані результати

| Сценарій | Фактичний результат |
| --- | --- |
| Збій саме вставки job | MySQL `BEFORE INSERT ON jobs` trigger з `SIGNAL SQLSTATE '45000'`. Доставка повернула `sent`; inbox=1, intent=1, jobs=0. Обробник: selected=1, failed=1, queued=0; queued_at=null, attempts=1, next_attempt_at через 60 с |
| Пауза повтору | Негайний повтор: selected=0; inbox і намір незмінні |
| Відновлення черги | Trigger видалено. Для контрольованого приймання next_attempt_at пересунуто в минуле лише в ізольованій БД. Обробник: queued=1, jobs=1; повтор: selected=0, jobs=1 |
| Нормальна доставка | Чинний worker виконав job; Mailpit: один лист на початкову синтетичну адресу. jobs=0. Повторна диспетчеризація: selected=0; inbox=1 |
| Згода false під час inbox-доставки | Новий inbox та sent; нового наміру/job немає |
| Відкликання згоди після handoff | Через чинний ProfileService вимкнено згоду; worker завершив job без нового листа |
| Зміна адреси після запису наміру | Через ProfileService змінено адресу, потім нову адресу підтверджено й окремо ввімкнено згоду. Обробник передав старий fingerprint; worker завершив job без листа на стару чи нову адресу |
| Mailpit після перевірок згоди/адреси | Початкова адреса: 1 лист; змінена: 0 |
| Два паралельні обробники | Третє MySQL-з'єднання тримало row lock на pending intent 5 с. Обидва окремі Artisan-процеси вибрали той самий ID. Після відпускання: перший selected=1/queued=1, другий selected=1/skipped=1; у БД один job |
| Збій після INSERT job, перед комітом | `BEFORE UPDATE` trigger забороняв queued_at для одного конкретного наміру. Вставлений job відкотився, queued_at лишився null; наступний здоровий намір у тому самому пакеті успішно передано (selected=2, queued=1, failed=1) |
| Повтор після збою маркера | Trigger видалено, час повтору пересунуто в минуле; створено лише один job проблемного наміру. Подальший запуск selected=0. Усі три jobs із цього та паралельного сценарію виконані worker |
| Непідтверджений профіль | Навіть із true у полі згоди новий inbox доставлено без нового наміру/job |
| Rollback зовнішньої композиції | processWithinTransaction усередині явної транзакції, потім rollback: нагадування лишилося scheduled, inbox=0, нового наміру немає |
| Команда і Scheduler | schedule:list показав новий щохвилинний виклик поряд із чинними. --limit=0: код виходу 2, без запуску пакета |

Після додаткових позитивних сценаріїв Mailpit має 1 лист на початкову адресу
і 3 на змінену — це окремі нові нагадування паралельного/атомарного приймання,
створені вже після зміни профілю. Старий лист на нову адресу не перенаправлявся.
Діагностика збою містила тільки фіксовані повідомлення та `intent_id`.

Додатково виконано Pint для змінених PHP-файлів, PHP syntax lint та
`git diff --check`. Тести не запускалися. Тимчасову MySQL після перевірки зупинено.
