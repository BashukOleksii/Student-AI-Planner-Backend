## Команди

Виконувати з кореня backend. Старий режим без `--attention` не змінено й для цих
сценаріїв він не потрібний: він має інший префікс `[DEMO-PLANNING]`.

Поточний A, без запису:

```bash
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention=A --dry-run
```

Безпечний повтор уже підготовленого A:

```bash
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention=A --database=student_planner --server-uuid=1d83fa0c-b8f4-11f1-95a9-b607627c265d --apply
```

Примусово повторити **штатну** перевірку тільки цього власника, не змінюючи fixture:

```bash
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention=A --step=check --database=student_planner --server-uuid=1d83fa0c-b8f4-11f1-95a9-b607627c265d --apply
```

Огляд може застаріти через звичайний перебіг часу та інші сесії акаунта. Якщо поточний
огляд прострочений без зміни вихідних даних, використайте штатну дію отримання нового
огляду в UI; команда не обходить дедуплікацію чи політику оновлення.

Після завершення ручної перевірки A спочатку вкажіть результат Session 148. Якщо
демонстраційна робота вже виконала свою роль, окремо завершіть Task 72 через UI.
Не змінюйте реальні сесії 75/112, якщо не знаєте їхнього результату. Якщо не хочете
завершувати A, наступний fixture не створюється. Ніякого автоматичного очищення немає.

Підготувати наступний сценарій, наприклад C:

```bash
demo_case='C'
demo_db='student_planner'
demo_server_uuid='1d83fa0c-b8f4-11f1-95a9-b607627c265d'
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention="$demo_case" --dry-run
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention="$demo_case" --database="$demo_db" --server-uuid="$demo_server_uuid" --apply
```

Значення БД/UUID треба звірити з **поточним dry-run**, а не переносити на інше
середовище. Запис відмовляє без `--apply`, exact email та exact ідентичності сервера.
Перед записом власник повторно завантажується під owner-first блокуванням.
Неправильний email, не-local середовище, неоднозначний marker або недопустимі умови
не створюють акаунт чи допоміжні записи для примусового успіху.

Для B/C/D/E/H `prepare` спочатку зберігає **одну валідну майбутню сесію** через
чинний planner і його confirmation writer. Переконайтеся в ручному переплануванні,
що початковий час ще не потребує заміни. Контрольований крок:

```bash
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention="$demo_case" --step=trigger --dry-run
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention="$demo_case" --step=trigger --database="$demo_db" --server-uuid="$demo_server_uuid" --apply
```

`trigger` змінює **лише дедлайн цього DEMO-завдання через TaskService**. Він не
переносить сесію. Якщо фактичний штатний review після цієї зміни не відтворює випадок,
транзакція зміни дедлайну відкочується. Глобальних змін не потрібно: `global_changes=[]`.
Dry-run показує ID, попередній і новий дедлайн, вихідні часи, пробні заміни й передумови.
Capacity probe використовує той самий allocator на чинному календарі, без запису,
вигаданих реальних ID чи збережених оглядів. Пробні рядки не є підтвердженим результатом.

Повернення контрольованої зміни **до застосування огляду**: відкрити
`/tasks/<фактичний task_id>`, очистити поле дедлайну (початкове значення `null` із
`manifest.initial_deadline`) і зберегти. Для повернення саме кроку H `stale`
відновити `proposed_task_change.deadline_before` із dry-run у часовому поясі профілю.
Потім отримати новий огляд. Після застосованого перенесення не переписуйте історію:
зміна дедлайну не повертає початкову сесію в `planned`.

Для H **після trigger**, коли огляд із заміною вже відкритий:

```bash
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention=H --step=stale --dry-run
php artisan planning:demo-seed --user=id:10 --expect-email=o@email.com --attention=H --step=stale --database="$demo_db" --server-uuid="$demo_server_uuid" --apply
```

Цей крок змінює дедлайн через той самий TaskService так, щоб попередня заміна більше
не вкладалася в допустимий час. Поверніться до старого огляду й спробуйте підтвердити.
Очікується відхилення застарілого результату, без часткового перенесення й без
автоматичного повтору POST. Для нової дії отримайте новий огляд.

## Де автоматичний огляд, а де ручний маршрут

Детектор має **одну** актуальну пропозицію для власника. Пріоритети з коду:
`decision_required` → `replan` → warning для непридатних до перенесення джерел →
`create_plan` → інші warning. B/C/D/E не є окремими типами: це результати рядків
одного `replan`. На чистому ізольованому власнику trigger B/C/D/E/H справді породжує
`replan`; усі заміни й згоди формують штатні сервіси, не демокоманда.

Під поточним o A реально видно автоматично. B–H в акаунт не записані; навіть після
підготовки їхній окремий auto-card може бути відсутній через 75/112 та інші проблеми.
Тому таблиця дає **підтримувані ручні** маршрути, а не обіцянку окремої auto-картки.
У створеному автоматичному replan можуть також бути проблеми інших завдань; для
чіткого ручного випадку вибирайте конкретне DEMO-завдання.

F/G на ізольованому власнику дають інформаційне `create_plan`. Воно не збільшує
attention_count як проблема, але має інформаційну групу/рекомендацію. Внизу сторінки
є «Створити план вручну» та «Відновлення окремої роботи». Під o ця рекомендація не
гарантується, поки існують пріоритетніші проблеми. Не підміняйте через це API.

**Межа пагінації F:** `StudyProposal.vue`/`PlanPreviewView.vue` зараз не мають
пагінації запропонованих сесій. Дані дозволяють перевірити 6 рядків, але саме
перемикання сторінок цього огляду відтворити неможливо без зміни UI, яку тут
заборонено. У `PlanningView.vue` є сторінки по 3 сесії на групу найближчого тижня,
а в `StudySessionsView.vue` — перемикання днів. Після явного збереження F відкрийте
список за **13.11–13.12** і перевірте перехід між 15 та 20 листопада; п’ять нових
сесій 20.11 виходять за поточний автоматичний семиденний горизонт.

## Запобіжники й перевірки

- Нові Task мають `[DEMO-ATTENTION]`, а нові сесії прив’язані тільки до цих Task; акаунти, паролі, глобальні preferences,
  timezone, availability і уроки не створюються й не редагуються.
- Future source для B–E/H підбирається всередині поточного фактичного auto-horizon
  та після 900-секундного lead. Нових недопустимих слотів «для демонстрації» немає.
- Якщо умов немає, `ready=false`, ID `null`, записів немає. Якщо змінені результати
  ручної перевірки, команда відмовляється їх ремонтувати. Повторний prepare — читання.
- Якщо після commit fixture перевірка не виконалася, `detector_error` прямо говорить,
  що дані вже збережено, й пропонує `--step=check`. Це не видається за rollback.
- Dry-run перевірений як SELECT-only, без `FOR UPDATE` та будь-яких записів; ID
  пробного work-unit не виходить у звіт як реальний ID. Tokens не друкуються.
- Backend: `scripts/testing/phpunit-disposable-mysql.sh --filter 'AttentionDemoTest|PlanningDemoCommandTest|PlanningAttentionTest'`.
  **25/25 тестів, 736 assertions**, тільки fresh disposable MySQL, ніякого PHPUnit на `student_planner`.
- Frontend: `npm test -- planning.test.ts planning-attention.test.ts recovery-ui.test.ts`:
  **90/90**. «Перевіряємо», помилка й «Немає дій» перевірено тут та у
  `PlanningAttentionTest` ізольовано, без штучних записів станів під o.
- Нові інтеграційні тести перевіряють всі A–H, validity до trigger, реальні заміни,
  точний залишок, окремі згоди, stale 409, owner/database guard, незмінність старої
  історії після recovery confirmation, відмову за несприятливих умов і rollback.

Зміни: `SeedPlanningDemo.php` (окремі опції), `AttentionDemoService.php`,
`AttentionDemoTest.php`, цей звіт і посилання з наявної інструкції демоданих.
Frontend, алгоритм, Resources, схема та старий `PlanningDemoService` не змінювалися.
