# Українська серверна відповідь AI: розклад на одну дату

`AgentOrchestrator` використовує чинний `get_schedule_for_date` та
`ScheduleAnswerPresenter` для вузького сценарію перегляду розкладу. Модель і далі
обирає інструмент; сервер не викликає нових інструментів, не змінює добір занять,
не перекладає відповідь другим запитом і не розширює можливості AI.

## Межа підтримки

Серверний шаблон застосовується лише за одночасного виконання всіх умов:

- Поточне повідомлення — самодостатня команда з обмеженого переліку нижче.
- У першій відповіді провайдера рівно один виклик: `get_schedule_for_date`.
- Аргументи містять лише `date`, що точно збігається з датою поточного запиту.
- Немає інших інструментів чи спроб підготовки зміни в цьому ході.

Підтримані форми (без урахування регістру, з необов'язковим кінцевим `?`, `.`
або `!`):

```text
Покажи [мій] розклад [на] <дата>
Який [у мене] розклад [на] <дата>
Show [me] [my] schedule [for] <дата>
```

Квадратні дужки тут позначають необов'язкові слова. Дата — коректна `YYYY-MM-DD`,
`сьогодні`, `завтра`, `today` або `tomorrow`. Відносна дата обчислюється за
збереженим часовим поясом користувача та тим самим зафіксованим UTC-часом, який
передано до інструкцій моделі. Використовуються звичайні пробіли між словами;
зовнішні пробіли обрізаються.

Це навмисно обмежений перелік, а не класифікатор довільної природної мови.
Діапазони, кілька дат, додаткові умови, інші формулювання, контекстні продовження
на кшталт «а завтра?», змішані прохання та підготовка змін залишаються у чинному
потоці провайдера. Так само шаблон не застосовується при кількох викликах,
виклику в пізнішому раунді, іншій даті або відсутності потрібного виклику.
Наприклад, «Покажи розклад на 2026-11-16 і зміни аудиторію…» не отримує шаблон,
навіть якщо модель спочатку читає лише розклад. Сам факт виклику інструмента чи
довільний текст моделі не є достатньою підставою для заміни відповіді.

## Дані та видимий текст

Дані надходять через чинний `ToolExecutor` з авторизованим власником до
`EffectiveScheduleReadService`; правила календаря, замін, семестрів і доступу
залишаються там. Presenter перевіряє `tool`, `ok`, список `data.lessons`,
`meta.timezone`, обидві межі дати, `limit`, `returned`, `total`, `truncated`.
Ліміт береться з `EffectiveScheduleReadService::LIMIT`. Для кожного заняття
перевіряються доступні зв'язки предмета/викладача, тип, аудиторія та коректні
ISO-моменти з часовим поясом. Інтервал має бути додатним і перетинати запитану
локальну дату. Presenter не обчислює склад розкладу повторно.

Три результати:

1. Заняття є: український заголовок, локальні часи, назва предмета, українська
   назва типу, викладач та аудиторія, якщо вони відомі. Назви, імена й аудиторії
   відтворюються без перекладу, зокрема `Linear Algebra`, `John Doe`, `B-12`.
   Невідомі предмет/тип позначаються явно, тип не виводиться з припущень.
2. Перевірений успішний результат із `total = returned = 0`:
   «На цю дату занять немає.» після заголовка з датою й часовим поясом.
3. Структурована помилка інструмента або некоректний результат:
   «Не вдалося отримати розклад на цю дату. Спробуйте ще раз пізніше.»
   Збій не перетворюється на порожній день; текст винятку не відображається.

Для обрізаного результату явно вказано кількість показаних і загальну кількість
занять. Для переходу через північ відображається також дата відповідного кінця
інтервалу; ненульові секунди зберігаються. Завелика відповідь понад чинні 16000
символів повертає коротке повідомлення про невдале отримання, замість розбіжності
між відповіддю надсилання й обрізаною історією. Збої до отримання структурованого
результату (наприклад, недоступний провайдер) використовують чинні API-помилки.

## Збереження та сумісність

Після придатного виклику оркестратор завершує хід без другого звернення до моделі.
Проміжний видимий текст моделі прибирається з нових подій цього ходу, зберігаються
виклик і результат; додається фінальне assistant-повідомлення з серверним текстом
та порожнім provider state. Нативний стан викликів зберігається для продовження
історії (зокрема підписані виклики Gemini); OpenAI message items із проміжним
текстом вилучаються за чинним підходом оркестратора.

`AiConversationService::finish` атомарно зберігає цей текст як повідомлення та як
результат ходу. Історія читає збережений `content`; повтор того самого запиту з
тим самим `Idempotency-Key` повертає збережений результат без нового виклику
провайдера. Маркери `proposal_ready` / `proposal_not_created` не додаються до
звичайної відповіді про розклад. Формат REST, ресурси, картки й механізм явного
підтвердження змін не змінено. Міграція не потрібна.

Старі AI-повідомлення та «Вхідні» не переписуються. Немає пошуку чи заміни старих
англійських рядків нагадувань і фільтра за латиницею. Решта вільних відповідей AI
не має серверної гарантії української мови.

## Ручна перевірка

Фактично перевірено 14.11.2026 через локальний HTTP Backend, cookie/CSRF та
ізольований MySQL 8.4.10 на окремому Unix socket. Чинні міграції застосовано лише
до нової тимчасової БД. Тимчасовий провайдер поза репозиторієм реалізовував чинний
`LlmProvider`: повертав вручну задані виклики та навмисно англійський текст;
інструменти, читання календаря, збереження, історія й повтор працювали справжні.
Реальних запитів до AI чи SMTP не було. Це ручне приймання HTTP API з контрольованим
провайдером; це не браузерне приймання й не перевірка вибору інструментів живою моделлю.

| Сценарій | Фактичний результат |
| --- | --- |
| `Покажи мій розклад на 2026-11-16`, заняття 09:00–10:30, Europe/Kyiv | Український шаблон; `Linear Algebra`, `John Doe`, `B-12` збережені дослівно; англійська преамбула моделі відсутня в історії |
| `Show my schedule for 2026-11-17`, немає занять | Українське повідомлення про порожній день |
| `Покажи розклад на 2026-11-18`, помилка читання | Коротка українська помилка, `tools[].error_code = execution_failed`, немає сирого винятку чи твердження про порожній день |
| GET історії та повтор із тим самим ключем для заняття й помилки | Той самий фінальний текст; відповідь повтору збігається з початковою; для першого повтору лічильник викликів провайдера не збільшився |
| Перегляд і зміна аудиторії на B-14 одним повідомленням | Чинна картка `confirmation_required` / `proposal_ready`; GET заняття все ще повертає B-12, підтвердження не виконувалося |

Помилку отримано справжнім читанням спеціально некоректного локального fixture:
заняття власника посилається на академічний період іншого власника. Чинна перевірка
зв'язків відхилила читання; чужі дані не відобразилися у відповіді.

Для повторення у звичайному локальному середовищі створіть власне заняття з
латинською назвою та оберіть окремий порожній день. Через автентифікований клієнт:

```http
POST /api/ai/conversations
Content-Type: application/json

{}
```

```http
POST /api/ai/conversations/{id}/messages
Content-Type: application/json
Idempotency-Key: 11111111-1111-4111-8111-111111111111

{"content":"Покажи мій розклад на 2026-11-16"}
```

Повторіть останній запит без зміни тіла/ключа; відкрийте
`GET /api/ai/conversations/{id}/messages` або знову відкрийте чат. Для інших ходів
використовуйте новий ключ. Перевірте порожній день, контрольовану помилку читання
на тимчасових даних і змішаний запит зі зміною аудиторії. Помилку не імітуйте
відповіддю «немає занять»; використовуйте безпечний структурований збій інструмента.

З живими Gemini/OpenAI та у браузері ці сценарії ще не перевірено. Відносні дати,
DST/північ, семестрові заняття, обрізання понад ліміт, некоректні результати та
продовження нативної історії після такого ходу оцінено за кодом, окреме ручне
приймання для них не виконувалося. Автоматизовані тести не додавалися, не
редагувалися й не запускалися.
