# Добровільні поштові нагадування

Email — другий канал чинного нагадування. Час спрацювання, типи, перевірки
цілі, AI й доставка у «Вхідні» залишаються чинними. `sent` / «Надіслане»
означає доставку в застосунок, а не успішний SMTP чи прочитаний лист.

## Контракт профілю для Frontend

Спільний `UserResource` у GET/PATCH `/api/profile`, реєстрації, вході й
підтвердженні адреси додатково повертає boolean `reminder_email_enabled`.
Міграція `2026_11_14_000001_add_reminder_email_preferences_to_users` задає
`false` для нових і наявних акаунтів без зміни їхнього підтвердження email.

```json
{"data":{"id":12,"name":"Студент","email":"student@example.test","email_verified":true,"reminder_email_enabled":false,"timezone":"Europe/Kyiv"}}
```

Перемикач «Отримувати нагадування на пошту» використовує чинний Sanctum
cookie/CSRF API профілю:

```http
PATCH /api/profile
Accept: application/json
Content-Type: application/json
X-XSRF-TOKEN: <чинний CSRF token>

{"reminder_email_enabled":true}
```

HTTP 200 повертає актуальний профіль. Поле необов'язкове: відсутність зберігає
поточне значення; `false` вимикає канал. Приймаються лише JSON `true` / `false`;
`null`, рядки й числа дають стандартний HTTP 422. Непідтверджений email при
спробі ввімкнення дає HTTP 422, `errors.reminder_email_enabled`:
`Спочатку підтвердьте поточну email-адресу.` Перевірка виконується в Service
після повторного читання профілю під блокуванням, а не зі старої моделі сесії.

Фактична зміна email атомарно скидає `email_verified_at`, вимикає опцію та
збільшує внутрішню `reminder_email_version`. Ця версія не приймається з API
і не серіалізується. PATCH із новим email та одночасним `true` відхиляється
повністю з 422: спочатку змінити адресу, підтвердити її чинним механізмом,
потім окремо ввімкнути канал. Незмінний email, ім'я й часовий пояс не вимикають
опцію. Саме підтвердження адреси не вмикає її автоматично.

Frontend має показувати отриманий серверний стан, блокувати ввімкнення до
підтвердження адреси та пояснювати потрібну дію. Тіло нагадування не отримує
полів каналу чи адреси одержувача. Вона береться виключно з поточного профілю.
Frontend, лист підтвердження і відновлення пароля в цій зміні не редагуються.

## Надійність черги й повторне читання адреси

`ReminderDeliveryService` під чинним owner-first блокуванням створює одне
сповіщення, переводить нагадування у `sent` і, лише для ввімкненої опції та
підтвердженої адреси, викликає `ReminderEmailService::enqueue()`.

Використано чинну таблицю InnoDB `jobs`, а не новий outbox. Окреме ім'я
queue connection `reminder-email` явно задає `database`, `connection=null`
(те саме default-з'єднання домену), `table=jobs`, `queue=reminder-email`,
`after_commit=false`. Воно не залежить від `QUEUE_CONNECTION` чи
`DB_QUEUE_CONNECTION` інших робіт. Service додатково перевіряє тотожність
об'єкта DB connection; job має `beforeCommit()`. INSERT роботи відбувається
негайно в тій самій транзакції, що й сповіщення та статус. Worker бачить
роботу тільки після коміту; rollback скасовує всі три записи. Падіння процесу
після коміту залишає роботу в БД. Callback після коміту не використовується.

Чинний унікальний `notifications.reminder_id`, блокування користувача та
перевірка `scheduled` не дозволяють повторному диспетчеру створити ще одне
сповіщення чи початкове поштове завдання. Увімкнення опції пізніше не надсилає
історичні нагадування. Повтори тієї самої роботи не є новими намірами доставки.

Зашифрований job містить лише ID власника, ID сповіщення та SHA-256 від
адреси разом із її внутрішньою версією; ані одержувач, ані текст листа в ньому
не зберігаються. Worker перечитує власника та його власне сповіщення. Якщо
опцію вимкнено, адресу не підтверджено, відбиток змінився або дані видалено,
робота завершується без листа. Зміна адреси A → B → A також анулює старий job.
Навіть повторне підтвердження й увімкнення нової адреси не перенаправляє йому
старе нагадування.

SMTP викликається тільки worker, поза будь-якою транзакцією БД. Worker не
бере User lock і не змінює нагадування або «Вхідні». Після перевірки snapshot
та підготовки mailer він безпосередньо перед SMTP заново читає профіль у
режимі autocommit і перевіряє опцію, підтвердження й відбиток адреси.
Зміна адреси, закомічена до цієї перевірки, скасовує лист. Між остаточним
читанням і зовнішнім SMTP залишається неминуче вікно: конкурентна зміна
профілю після перевірки не може відкликати вже розпочате надсилання.
Нову адресу такий job ніколи не підставляє. Чинний transport timeout —
15 секунд; job timeout — 60.

Текст береться з незмінного inbox snapshot і повторно перевіряється через
`ReminderDeliveryRules::stored()`. Тема — «Навчальне нагадування», окремі
українські HTML/plain-text шаблони. HTML екранує текст користувача. Чинні
тексти нагадувань, зокрема резервні, не перекладаються й не змінюються.
Використано явно `Mail::mailer('smtp')` із перевіркою фактично створеного
SMTP transport (зокрема після застосування `MAIL_URL`), без `log` або log-failover: вміст
листів не потрапляє в журнал через поштовий транспорт. Job замінює будь-яку
помилку фіксованим `Reminder email delivery failed.` без оригінального винятку,
щоб worker/failed_jobs не отримували SMTP-секрети, текст чи адресу.

## Межа SMTP та політика повторів

До трьох спроб на job, паузи 60 і 300 секунд, timeout 60 секунд при
`retry_after=90`. Кожна спроба заново перевіряє профіль. Після третього збою
робота залишається у чинній `failed_jobs`; автоматичних нескінченних повторів
немає. SMTP-збій не змінює збережене сповіщення, `sent` або `sent_at`.

Гарантії «рівно один лист» немає. SMTP міг прийняти лист до втрати відповіді,
або worker може впасти після надсилання, але до видалення job. Повтор у такому
разі здатен дати дублікат. Застосунок гарантує один inbox record і один
початковий намір у черзі, а не одноразову зовнішню доставку. Ручний
`queue:retry <uuid>` запускає новий цикл спроб і теж може дублювати вже
прийнятий лист; його застосовують лише після розгляду невизначеного результату.

## Локальний запуск

Застосувати лише нову міграцію до локальної MySQL:

```sh
php artisan migrate --path=database/migrations/2026_11_14_000001_add_reminder_email_preferences_to_users.php --no-interaction
```

Mailpit: SMTP `127.0.0.1:1025`, UI/API `http://127.0.0.1:8025`.
Для локальних процесів потрібні `MAIL_HOST=127.0.0.1`, `MAIL_PORT=1025`,
`MAIL_SCHEME=null`, `MAIL_URL=null`, порожні `MAIL_USERNAME`, `MAIL_PASSWORD` і
локальна `MAIL_FROM_ADDRESS`. Чинні SMTP/.env цього завдання не змінювалися.
За наявності config cache процесні env-перевизначення не діють — не
використовувати production cache для цієї перевірки.

В окремих терміналах:

```sh
php artisan serve --host=127.0.0.1 --port=8000
php artisan schedule:work
php artisan queue:work reminder-email --queue=reminder-email --sleep=3 --tries=3 --timeout=60
```

Scheduler як раніше викликає диспетчер щохвилини. Для контрольованої ручної
перевірки не запускати поштовий worker постійно, а виконувати по одній роботі:

```sh
php artisan reminders:dispatch-due --limit=100
php artisan queue:work reminder-email --queue=reminder-email --once --tries=3 --timeout=60 --no-ansi
```

Звичайний worker для `default` не споживає `reminder-email`; він потрібен і
надалі для чинних робіт застосунку. Scheduler без поштового worker створює
«Вхідні» та надійно накопичує поштові роботи, але листи ще не надсилає.
